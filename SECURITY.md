# SDBX security policy

SDBX controls Docker Compose workloads, authentication policy, VPN routing, and
secret-bearing project files. Treat a vulnerability in SDBX as potentially
affecting host confidentiality, integrity, or availability.

The detailed adversary, asset, abuse-case, and residual-risk analysis lives in
the [threat model](docs/threat-model.md).

## Supported versions

`v1.0.0-RC1` is the current published release candidate. RC2 is under
development and has not superseded RC1. Release candidates
receive security fixes while they are the current published line, but their
public interfaces may still change before v1 stable.

| Version | Security support |
|---|---|
| `1.0.0-RC1` | Current published RC; supported during its evaluation period |
| `1.0.0-RC2` | Unreleased candidate; acceptance in progress |
| Older or private development builds | Unsupported |

Security fixes will target the latest supported release; users may need to
upgrade to receive them.

## Report a vulnerability privately

Do not open a public issue, discussion, or pull request for a suspected
vulnerability.

Use [GitHub private vulnerability reporting](https://github.com/get-sdbx/sdbx/security/advisories/new).
This creates a private draft advisory visible only to the reporter and SDBX
maintainers. Do not infer a working mailbox from the project domain.

Include:

- the affected SDBX version and commit;
- host OS, architecture, Docker Engine, and Compose versions;
- the exposure mode and relevant service definitions;
- a minimal reproduction and expected impact;
- whether credentials, project files, backups, containers, or the host may
  have been exposed;
- logs with tokens, passwords, identities, private keys, cookies, domains, and
  personal data removed.

Do not send real VPN credentials, Authelia secrets, age identities,
passphrases, service API keys, or production exports. Use synthetic examples.

## Response targets

These are targets, not contractual service-level agreements:

| Stage | Target |
|---|---|
| Acknowledge receipt | Three business days |
| Confirm scope and severity | Seven business days |
| Provide next update | At least every seven business days while active |
| Coordinate disclosure | After a fix and upgrade path are available |

The maintainer may request additional time when a coordinated dependency or
container-image fix is required.

## Scope

### In scope

- the `sdbx` CLI and `sdbxd` daemon;
- the management broker and host Dashboard;
- official embedded service definitions and generated configuration;
- lock, source-verification, update, rollback, backup, and restore behavior;
- path, permission, symlink, archive, parsing, routing, and command-injection
  boundaries;
- authentication and authorization policy generated by SDBX;
- VPN enforcement behavior claimed by SDBX.

### Generally out of scope

- vulnerabilities solely in third-party container images or upstream
  applications, unless SDBX configures or exposes them unsafely;
- compromised hosts, Docker daemons, root accounts, or maintainer signing keys;
- social engineering and denial-of-service tests against public infrastructure;
- reports that depend on stolen credentials without an SDBX weakness;
- legal disputes about user-selected media sources.

For an upstream image vulnerability, report it to the upstream project first.
Tell SDBX privately when the catalog pin, generated policy, or upgrade path
also needs to change.

## Trust boundaries

### Docker and the host

Docker control is root-equivalent. A user able to operate the Docker daemon can
normally mount host files, change container privileges, and affect every SDBX
service.

`sdbxd` intentionally runs as root because it owns host and Docker operations.
The daemon registers one explicit project and verifies its configuration,
schema-v2 lock, active graph, and generated-file digests before allowing a
mutation.

Do not expose the Docker socket over TCP. Official containers do not receive
it at all: Traefik consumes deterministic file-provider routes generated from
the verified service graph, and catalog validation rejects authored or
rendered Docker-socket mounts.

### Management Dashboard

The default `sdbx serve` listener is loopback-only. The packaged remote service
uses a host listener protected by TLS 1.3 mutual authentication from generated
Traefik configuration, after Authelia authorizes an administrator. There is no
in-cluster Dashboard mode and the Dashboard has no direct project, filesystem,
or Docker operator.

The packaged service also exposes a distinct loopback-only recovery listener
on port `18778`. It is reachable remotely only through an operator-created SSH
tunnel and still requires the out-of-band browser token printed by
`sdbx console --addr 127.0.0.1:18778`.

The browser-facing process talks to `sdbxd` through a protected Unix socket and
broker client-token file. A distinct browser token is provisioned in
`/run/sdbx/console.token`. `sdbx console` places it only in a URL fragment; the
browser removes that fragment from the address bar, keeps the credential in
session storage, and sends it on every management API request. Unauthenticated
HTML and static assets contain no credential or management data. Forged
`Origin` and `Sec-Fetch-Site` headers do not replace token possession.

The broker API is versioned and typed; it has no arbitrary command, Docker API,
filesystem path, mount, or container-exec primitive.

The local static client token represents an administrative client. If the Web
UI process or its token is compromised, the attacker can request supported
typed mutations. The blast radius is reduced by project scope, lock/digest
preflight, exact confirmations, request/response bounds, timeouts, audit
records, and the absence of arbitrary host primitives; it is not reduced to
read-only access.

Optional OIDC authorization verifies issuer, signature, audience, expiry,
subject, groups, and authentication time. Mutations require the `sdbx-admin`
group; high-impact actions require recent authentication.

The bundled Dashboard uses the separate static browser token to authenticate
the local HTTP client and the broker token only on its Unix-socket hop.
Optional OIDC enables direct broker clients; it does not add an OIDC login flow
to `sdbx serve`.

### Route authentication

Authentication is declared per routed service:

- `admin-only` and `protected` routes use Authelia ForwardAuth;
- `native-auth` routes rely on the application's own account system;
- `public` routes intentionally have no user authentication.

Plex, Jellyfin, and other native-auth applications are not automatically
protected by Authelia. Configure their native administrators before exposing
them.

Sonarr, Radarr, Lidarr, Prowlarr, and Whisparr use layered authentication. Their
public routes remain `admin-only` behind Authelia, and SDBX also reconciles
native Forms credentials with authentication required from every address. This
second boundary prevents a Docker-network peer from bypassing the edge by
calling the application directly. Retrieve a managed credential only from a
private terminal with `sdbx secrets show SERVICE --confirm reveal`.

The generated Authelia default policy is deny. ForwardAuth rules use the typed
`auth.factor` project setting. It defaults to `one_factor` for initial TOTP
enrollment; after enrollment, operators can regenerate the complete
ForwardAuth boundary as `two_factor`.

Authelia's ForwardAuth session cookie is scoped to the configured SDBX domain
so it can authenticate multiple service hosts. Any routed application on a
covered host receives browser cookies for that scope at its HTTP boundary,
even when JavaScript cannot read an `HttpOnly` cookie. Traefik cannot
selectively remove one request cookie without also breaking application-owned
session cookies. Treat every routed image as trusted to receive domain-scoped
browser traffic; external sources therefore require an exact
`route:AUTH-MODE` declaration and operator grant.

### Service catalog and external sources

The complete official catalog is embedded in the binary.

External Git sources are optional. They must pin an immutable commit and
signature and receive explicit catalog-permission and image-registry
allowlists. A trusted external definition can still request powerful container
capabilities within those grants. Review the exact source, commit, signer,
permissions, registries, volumes, devices, capabilities, and networking before
locking it.

New sources start with an empty registry allowlist. SDBX displays the exact
URL, commit, signer, registry grants, and catalog-permission grants before it
persists a source; no public registry is trusted implicitly.

Git fetches use a private quota-bounded staging cache, bounded diagnostics, and
a fixed timeout. SDBX rejects oversized object stores or working trees, dirty
checkouts, and checkout symlinks before atomic promotion. A failed refresh
cannot replace the last verified checkout. The exact v1 limits are documented
in [External source trust](docs/external-sources.md).

Catalog discovery is also bounded before YAML parsing by entry, depth, file,
tree-byte, definition-count, and aggregate-definition-byte limits. This
prevents a large set of individually small signed definitions from becoming
unbounded parse work.

Local sources are development inputs. A lock containing local source material
is not equivalent to a signed third-party release.

### Secrets

SDBX generates cryptographic secrets with `crypto/rand`, writes managed secret
files atomically, rejects unsafe symlink targets, and creates the secret
directory with restrictive permissions.

User-supplied credentials such as VPN secrets and claim tokens are necessarily
available to the services that consume them. File permissions do not protect a
secret from root, Docker administrators, or a compromised consuming container.

Rotating an authentication or encryption secret can invalidate sessions or
make existing state unreadable. Take an encrypted backup and understand the
affected service before rotation. SDBX v1 intentionally does not expose a
generic file-only rotation command; use only a reviewed service-specific
procedure.

### Backups

Backups are always authenticated age-encrypted. They use either:

- an age public recipient, with the private identity kept separately; or
- a passphrase that SDBX does not store.

SDBX never creates a plaintext backup archive. An archive cannot be recovered
without its identity or passphrase.

Backup contents include SDBX configuration, secrets, managed service
configuration, Compose runtime, and the lock. They exclude the complete
configured `data_path`, including Authelia identity/TOTP state, plus media,
downloads, and external Docker volumes. Store archives, application-consistent
data snapshots, and recovery credentials separately and test their combined
restoration before depending on them.

Restore validates the complete decrypted archive before promotion, stages and
revalidates it through fixed root handles, journals each same-filesystem
promotion, and rolls the complete managed set back on failure. Interrupted
transactions recover before the next restore reads project intent. Every
restore preserves the verified target intent, lock, Compose, environment, and
generated policy; archive copies of those files are compatibility evidence and
never authorize runtime. `--relocate-managed-roots` permits only the archived
config and secret roots to differ while relocating compatible application
state. Follow the
[backup and restore runbook](docs/backup-restore.md), including application
snapshot and compatibility limits.

### VPN enforcement

When VPN is enabled, qBittorrent shares Gluetun's network namespace. If Gluetun
is unavailable, qBittorrent does not receive an independent application
network path.

Disabling VPN requires an explicit acknowledgement that torrent traffic will
use the host's public network. `sdbx vpn status` and `sdbx doctor` inspect the
configured and live posture, but an operator remains responsible for testing
the egress IP and provider behavior.

The non-destructive status check does not simulate tunnel loss. Release
qualification includes an isolated destructive kill-switch proof on a
disposable QA host; it must not be run against production.

## Security properties

The current codebase includes:

- strict YAML decoding with unknown-field rejection;
- bounded configuration, request, response, log, audit, and archive handling;
- managed-path validation and symlink rejection at sensitive file boundaries;
- immutable service-definition and OCI image locks;
- generated-file digest verification before privileged mutations;
- dependency-ordered updates with automatic runtime/lock rollback;
- transactional project initialization and interrupted-initializer recovery;
- policy-derived route authentication and TLS;
- segmented edge, application, download, and management networks;
- container capability dropping, read-only roots, `tmpfs`, PID limits, and
  resource bounds where supported by the upstream image;
- redacted append-only privileged-operation audit events;
- authenticated host/loopback listeners, Host-header, origin, CSP, framing,
  referrer, permission, and
  content-type defenses for the management UI;
- authenticated encrypted backups with guarded extraction and restore.

These controls reduce risk; they do not make arbitrary third-party services or
an internet-exposed media stack risk-free.

## Known limitations

- Docker and root remain high-value trust anchors.
- The local broker client token has administrative authority over the typed API.
- Root broker mutations preserve existing managed owners and make new managed
  paths inherit the nearest real parent. Broker socket, token, and audit files
  intentionally remain root-owned.
- The broker audit log is locally append-only while the process runs but is not
  remotely anchored or cryptographically tamper-evident.
- Native-auth services depend on upstream authentication quality and operator
  configuration.
- LAN TLS uses Traefik's local/default certificate; custom certificate-file
  configuration is not supported in v1, so clients may show a trust warning.
- Direct and Cloudflare exposure depend on public DNS and third-party
  infrastructure.
- Container images are independent upstream software with their own
  vulnerabilities and release practices.
- GitHub private vulnerability reporting must remain enabled for every
  supported public release.
- SDBX does not back up the configured `data_path`, including Authelia
  identity/TOTP state, media, downloads, or application-managed external
  volumes.

## Operational security baseline

Before exposure:

1. Protect SSH and host administrator access.
2. Restrict membership in the Docker and SDBX management groups.
3. Run `sdbx lock verify`, `sdbx doctor`, and `sdbx vpn status`.
4. Configure every native-auth service administrator.
5. Enroll and verify the administrator TOTP device, set `auth.factor` to
   `two_factor` when required, restart Authelia, and verify every generated
   ForwardAuth route in a fresh browser session.
6. Preserve an encrypted backup and its recovery credential separately.
7. Review public DNS, published host ports, Cloudflare configuration when used,
   and firewall rules.
8. Review the active route/auth/network evidence in the management console or
   CLI.

Do not paste `sdbx doctor --json`, logs, `.sdbx.yaml`, `.sdbx.lock`, audit
events, or generated Compose files into a public issue without reviewing them
for domains, paths, account identifiers, and other deployment metadata. SDBX
redacts common credential shapes from its log and diagnostic surfaces by
default, but novel or unlabeled upstream formats can evade a pattern filter.
Treat redaction as defence in depth, never as permission to publish output
without review.

## Security changes

Security-relevant changes will be documented in release notes and, when
appropriate, a GitHub Security Advisory. The public release process must
include:

- dependency and vulnerability scans;
- race-enabled tests;
- generated Compose validation across supported profiles;
- installer checksum verification;
- provenance and release-asset checks;
- a restore and rollback exercise;
- verification of the private reporting channel.
